# ESP32-S3 OV2640 手机直连监控

## 手控制器参数叠加（2026-10-03）

手机与手控制器同时连接相机热点。80 端口新增 `/ws/upload`（接收手控制器上传）、`/ws/view`（向网页推送），以及 `/api/telemetry`（只读诊断）；81 端口继续传输原视频。手控制器每 300 ms 上传，数据只用于显示，没有新增解锁、起飞等控制入口。

网页在每只眼的视频区域绘制血氧、**手控电压 V**、飞机 Pitch/Roll 和距离；单眼、双眼、全屏使用同一组真实数据。手控电压显示两位小数，不显示电量百分比。参数更新与过期检查独立于视频帧，视频暂停或卡顿时仍能清除过期读数。源数据不存在或无效显示 `--`，距离 0 与无效值不会混淆。

按用户最新要求，参数只显示数值和单位，取消背景框及参数标题，用细黑描边保持亮色画面上的可读性。血氧在左上、电压在右上、距离在左下，右下的两个角度依次为 Pitch、Roll；无障碍文字仍保留完整参数名称。

- 手控制器上传或飞机遥测超过 1200 ms：对应参数失效。
- 输入电压超过 5000 ms、血氧结果超过 10000 ms：对应参数失效。血氧源仍按约 5 秒窗口计算。
- 页面进入后台关闭参数连接；回到前台自动重连。前端断线后立即清除有效状态，每秒尝试重连。
- 相机在转发和首次连接快照时累计源数据年龄；浏览器继续按本地单调时钟累计，避免旧数据因重发变新。

`main/hud_server.c` 在 HTTP 服务任务内处理会话和快照，校验完整消息、字段类型、长度和序号。每个角色保留一个连接，新连接替换旧连接，断线缓存不会显示为有效。上传确认先发出，再向观看者推送；WebSocket socket 发送超时为 100 ms，避免慢客户端长时间阻塞。总 socket 预算调整为 16。

**“等待手控制器”修正（2026-10-03）：** 用户报告手控已开机但页面一直等待。双串口只读检查确认手控在持续上传、相机也在接收；问题是 ESP-IDF 6.0.1 起握手不再调用普通 WebSocket URI handler，旧的 `HTTP_GET` 初始化分支从未执行，因此发布者/观看者会话没有登记。现启用 `CONFIG_HTTPD_WS_POST_HANDSHAKE_CB_SUPPORT`，把初始化放到两个端点的 `ws_post_handshake_cb` 中，并拒绝没有会话的上传。来源：[Espressif 6.0 迁移说明](https://docs.espressif.com/projects/esp-idf/en/latest/esp32/migration-guides/release-6.x/6.0/protocols.html#websocket-handler-no-longer-called-during-handshake)。页面现在明确显示“手控已连接 · 飞机未回传”，避免把不同链路混淆。

新增 `tests/hud_server_selftest.c` 是真实相机服务的实机回归：用 TCP loopback 建立只接收数据的观看者连接，检查握手后首包、18 份来自真实手控的递增快照、旧观看者被替换后的持续推送。未伪造电压，也不发送任何控制命令。已实机通过，最后电压 5175 mV；证据保存在现有构建目录 `/home/zhangnuo/esp/builds/xiaofeiji-camera-s3/hud-selftest-runtime.log` 与 `hud-selftest-verification.json`。此检查覆盖实际 HTTPD/握手/推送，但不等于手机显示验证。

## 使用

1. 打开设备电源，在手机 Wi-Fi 列表连接 `Camera-D6A4`（实际名称末尾来自设备 MAC，本机实测为 D6A4），**无密码**。
2. 用 Safari 或 Chrome 打开 **`http://192.168.4.1/`**。监控网页在 80 端口，视频流由网页自动连接 81 端口。
3. 默认 320×240、帧率优先、双眼模式。手机横屏后可放入 VR 眼镜；也可切换单眼、画质和 VGA 640×480。

**iPhone 沉浸观看：** 本页把视频和参数合成到 canvas。iPhone 的普通网页元素全屏仍有[WebKit 平台限制](https://bugs.webkit.org/show_bug.cgi?id=206854)，不能套用原生 video 播放器的全屏接口。按钮会按能力选择系统“全屏”或“沉浸观看”；系统请求失败也自动进入沉浸观看，隐藏页面工具栏，保留参数及“退出观看”按钮。退出按钮不覆盖画面，横竖屏切换不重新连接视频。此模式不能强制隐藏 Safari 自己的地址栏。

希望去掉浏览器地址栏时，用 Safari 打开页面 → 分享 → 添加到主屏幕，再从主屏幕图标打开并横屏观看；若有“作为网页 App 打开”选项，保持开启。已加入旧版 iOS 所需的独立网页模式 meta 配置。[WebKit 主屏幕网页模式说明](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/#every-site-can-be-a-web-app-on-ios-and-ipados)。这不提供脱离相机热点的离线观看。

兼容检查：Chromium、WebKit 的系统全屏/退出、接口缺失、请求拒绝、旋转与缩小视口均通过；模拟参数在沉浸模式仍正常更新和过期，既有视频回归通过。这些是浏览器自动化检查，iPhone 实机的独立网页启动效果尚未由本端验证。

手机可能提示“此 Wi-Fi 无互联网”，保持连接即可。按用户要求取消 DNS 劫持和网络检测跳转，手动用浏览器打开上述地址。热点持续开启，重启后仍可用，不读取已保存的路由器凭据；烧录不会擦除 NVS。此模式下没有路由器局域网地址，也不能经互联网观看。

2026-10-03 手机布局修正：原页面按固定 150/215 px 扣除工具栏高度，按钮换行后底部会超出屏幕；在 844×390 横屏和 320×568 竖屏等尺寸已复现。现改为页面按动态视口高度布局，工具栏和底栏占实际高度，视频使用剩余空间，并为刘海/底部手势区留出安全边距。Chromium、WebKit 回归覆盖六种窗口尺寸、横竖屏切换、可用高度缩小、全屏/不支持时提示，确认控件与底栏均在视口内且视频继续播放；仍保留完整视频比例。修正版已烧录并通过写入哈希校验；启动日志为 `Camera: ESP_OK`，手控上传已恢复。本轮页面效果为浏览器自动化验证，不代表已在用户手机上完成复测。

热点最多允许两个设备加入，但视频只允许一个观看连接；第二个观看页面会收到 503。切换手机观看前先关闭电脑页面的视频。开放热点附近的人也能访问画面。

## 视频实现与限制

- 复用 Espressif `esp32-camera 2.1.7` OV2640 驱动，使用 `PIXFORMAT_JPEG`，不再由 ESP32 软件编码 JPEG。两个各 160KiB 的 PSRAM 帧缓冲区连续采集，选择最新帧；JPEG 复制到复用的 160KiB 发送缓冲区后及时归还采集帧。发送前检查长度、起止标记和文件头段边界。PSRAM 直连 DMA 保持关闭。
- CPU 240MHz、Octal PSRAM 80MHz、摄像头 XCLK 20MHz。OV2640 JPEG 质量 20 为帧率优先、12 为画质优先，数值越小细节越多；默认 QVGA，可切 VGA。状态 API 的 `encode_ms` 为 0，表示 ESP32 没有软件编码开销，不表示传感器内部编码没有耗时。
- 启动时先丢弃两帧，再检查最多三帧真实 JPEG 文件头；全部失败时报告 `ESP_ERR_INVALID_RESPONSE` 并停用视频采集，网页和参数服务仍启动。检查到 SOS 段为止，不代替完整图像解码。无效帧会在 USB 日志中打印前 32 字节，便于区分驱动识别成功与图像数据正常。
- 只从设备取一条 MJPEG 流；手机在同一画布左右各绘制一次。单摄像头两眼画面相同，没有立体景深。
- 网页用 `:81/stream?size=qvga&quality=fast&format=bytes` 获取 `application/octet-stream` 响应并解析 JPEG 帧。Apple WebKit 会取消通过 `fetch` 获取的 `multipart/x-mixed-replace` 响应，所以网页必须带 `format=bytes`；不带该参数的 `/stream` 保留标准 MJPEG 类型，供原生图像客户端使用。帧内容和采集流程相同。[WebKit 源码](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/loader/SubresourceLoader.cpp)
- 连接失败时，页面显示原始错误和步骤（fetch/read/parse/decode/render），并向 `/api/client-error` 回传到 USB 日志；日志标记为 `viewer: Client error`，便于区分网络和图像错误。
- 逐帧检查 JPEG 文件头的段长度；数据损坏时明确提示检查摄像头排线。正常 JPEG 若被 `createImageBitmap` 拒绝，则回退到原生 Image 加载；成功回退后持续使用 Image，不逐帧重试失败的 Bitmap 路径。两眼仍共用一个解码结果，上一帧的 Blob URL 随帧释放。
- 历史 GC2145 固件（2026-09-30）的 USB 日志实测：320×240 约 12–13 fps，640×480 约 2.7–3.1 fps，软件 JPEG 编码约需 65–70ms / 260–281ms。这不是当前 OV2640 的帧率；本次 OV2640 由于真实 JPEG 文件头损坏，尚不能测有效播放帧率。USB 日志每 5 秒报告发送帧率、采集和发送耗时，状态 API 提供耗时与累计发送帧数。

## 验证

`tests/browser.cjs` 使用真实 HTTP 服务覆盖分片解析、图像解码、左右眼绘制、单条流、画质/分辨率切换和停止重启；加 `--webkit` 可复现旧版 multipart fetch 失败并验证修复后的二进制响应。`tests/benchmark.py` 测实机帧率并逐帧校验 JPEG。`tests/live_browser.cjs` 检查实机持续播放、画质/分辨率切换和双眼模式。DNS 组件及其旧测试不再用于当前固件。

2026-09-26：OV2640 固件编译、浏览器模拟流测试、烧录写入校验通过。启动日志确认 OV2640 JPEG 双缓冲初始化成功；监控页返回 200，状态 API 为 ESP_OK，网络检测路径返回 404 且没有跳转。电脑定量测试因热点连接中断而未完成，随后按用户要求停止切换电脑网络，用户自行连接并确认性能正常。
