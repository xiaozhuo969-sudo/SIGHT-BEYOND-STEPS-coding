# STM32F103C8T6 遥控器固件恢复

这是从实际读取的固件整理出的 **可编译 C 重建工程**，并附原始机器码的反编译参考。原来的变量名、注释、文件划分和 Keil 工程配置无法从 BIN 找回。这里的函数名由分析重新命名；重编译结果也不会与原 BIN 逐字节相同。

原始资料在上一层：`STM32F103C8T6_backup.bin`、`.hex`、`.sha256`。BIN 共 65,536 字节；最后一个非 `FF` 字节在 `0x0800215F`，代码、常量和初始化数据总占用范围约 8.34 KiB。BIN 的 SHA-256：`cbe3d9ff29cbe4ed8b158dc277fd6280a572135573af9f70b42d96420f9ad43d`。

## 实现的功能

以下判断来自外设地址、调用链、常量和机器码仿真，不依赖文件夹名称。

| 功能 | 恢复结果及证据 | 确认程度 |
| --- | --- | --- |
| 四路模拟输入 | ADC1 扫描通道 0、1、2、3；DMA1 通道1循环传送到 `0x2000001E`，初始化函数 `0x0800026C` | 高 |
| 主控制通道转换 | 四路值缩放后加1000、微调，限制在1000～2000，函数 `0x080015C0` | 高，已仿真对照 |
| 平滑滤波 | CH0、CH1、CH3：`new = trunc(0.75 * previous + 0.25 * current)`；CH2没有此滤波 | 高，已仿真对照 |
| 四个辅助开关 | CH4～CH7在1000和2000之间切换；低电平按键，一次按下触发一次 | 高，已仿真对照 |
| 微调及掉电保存 | CH0/CH1每次加减5；调整前检查±250边界；写I²C设备的地址0/4 | 高，已仿真对照写入请求 |
| 无线发射 | NRF24L01兼容寄存器命令，软件SPI，发送32字节帧，函数 `0x08001098` | 高；实际模块型号未通过丝印核实 |
| 模块自检 | 无线TX地址写入5个`A5`再读回；EEPROM位置`0x55`写`AA`，约1秒后读回检查 | 高 |
| 时基与调度 | SYSCLK=48 MHz，SysTick装载47999；每11次SysTick执行控制处理，标称约90.9 Hz | 高，调度逻辑已仿真对照；阻塞会改变实际频率 |
| PA12状态输出 | 初始化为高，按键状态机写高/低；是否连接LED需看实物 | 输出行为高，物理用途未确认 |

本固件的主循环为空，主要业务都由 `SysTick_Handler` 调用：输入转换 → 按键处理 → 打包 → 无线发送。飞机的姿态控制和电机控制需要接收端固件实现。USART1中断只读取两次状态寄存器，没有恢复出实用的串口通信协议。

## 引脚和通道

引脚是根据GPIO地址和位掩码确认的；CH0～CH3对应横滚、俯仰、油门、偏航中的哪一项，需要接收端协议或实际摇杆接线才能确定。

| 用途 | STM32引脚 | 固件行为 |
| --- | --- | --- |
| CH0模拟输入 | PA3 / ADC通道3 | `1000 + trunc(ADC * 0.25) + trim[1]`，随后滤波、限幅 |
| CH1模拟输入 | PA2 / ADC通道2 | `1000 + trunc(ADC * 0.25) + trim[2]`，随后滤波、限幅 |
| CH2模拟输入 | PA1 / ADC通道1 | `1000 + trunc(ADC * 0.2) + trim[3]`，限幅，未滤波；trim[3]启动为0 |
| CH3模拟输入 | PA0 / ADC通道0 | `1000 + trunc(ADC * 0.25) + trim[4]`，随后滤波、限幅；trim[4]启动为0 |
| CH4开关 | PA15 | 低电平触发1000↔2000 |
| CH5开关 | PB11 | 低电平触发1000↔2000 |
| CH6开关 | PC14 | 低电平触发1000↔2000 |
| CH7开关 | PC15 | 低电平触发1000↔2000 |
| CH0微调减/加 | PA6 / PA7 | 每次−5/+5，写EEPROM地址0 |
| CH1微调减/加 | PB0 / PB1 | 每次−5/+5，写EEPROM地址4 |
| 软件I²C | PB6=SCL，PB7=SDA | 开漏，器件7位地址`0x50`，总线地址字节`A0/A1` |
| 软件SPI | PB13=SCK，PB15=MOSI，PB14=MISO | MSB先发 |
| 无线控制 | PA11=CE，PB12=CSN，PA8=IRQ | IRQ上拉、低电平有效 |
| 状态输出 | PA12 | 推挽输出 |

PA4也被配置为上拉输入，但按键扫描未使用。AFIO关闭JTAG、保留SWD，使PA15能作为按键。ADC时钟配置为48 MHz/8=6 MHz，采样时间编码5，对应55.5周期。

微调设备符合AT24C02类EEPROM的访问方式，但仅凭程序不能确定具体型号。0/4处各存一个**小端有符号16位数**。EEPROM独立于STM32内部Flash，因此原始64KB备份不包含板上EEPROM当前保存的微调值。

## 无线设置与32字节协议

TX地址和RX pipe0地址在固件中均为 `E1 E2 E3 E4 E5`，按此顺序写寄存器。初始化写入：

| 寄存器 | 值 | 含义 |
| --- | --- | --- |
| CONFIG | `0E` | 发射模式、上电、启用2字节CRC |
| EN_AA | `00` | 关闭自动应答 |
| EN_RXADDR | `01` | pipe0使能 |
| SETUP_RETR | `1A` | 配置自动重发延时和次数，但当前自动应答关闭，不能据此称有可靠重传 |
| RF_CH | `01` | 2401 MHz |
| RF_SETUP | `07` | 1 Mbps，0 dBm |

| 字节位置 | 原固件实际内容 |
| --- | --- |
| 0～3 | 固定初值 `AA AF 03 1B` |
| 4～19 | CH0～CH7，每通道2字节，高字节在前 |
| 20～21 | `AF AA`：原代码继续读取通道数组后的相邻RAM，读到了帧头前两字节 |
| 22～23 | `1B 03`：同样读到了帧头后两字节 |
| 24～25 | 刚写出的CH0两个字节反序，即低字节、高字节 |
| 26～30 | 初值0，已分析代码未修改 |
| 31 | 字节0～30的累加和，取低8位 |

额外字节20～25不是新增控制通道：原打包循环处理了11个半字，其中前8个来自通道数值所在的16字节区域，后3个实际读到了紧邻的发送帧。这个机器码行为已验证，**原C是否因数组越界造成此行为仍属于推断**。`remote_logic.c`显式模拟已确认的RAM读取行为，避免新的C数组越界，同时保留接收端可能依赖的实际帧格式。帧头类似常见的匿名上位机协议，但缺少接收端资料，不能据此认定采用了某个完整协议版本。

## 文件和构建

优先阅读这三个源码：

- `remote_logic.c/.h`：摇杆、滤波、按键、协议和调度逻辑。
- `firmware_main.c`：STM32时钟、ADC/DMA、软件I²C/SPI、EEPROM和无线驱动。
- `startup.c`：C启动代码和59项中断向量，配合`stm32f103c8.ld`。

`decompiled_reference.c`保存104个识别函数的Ghidra反编译参考，是伪C，**不作为编译输入**。其中Keil软件浮点库含内联分派，Ghidra仍报告一处解码警告；人工恢复的浮点业务逻辑已由机器码仿真核对。`function_map.json`提供函数地址和调用关系，`firmware_disassembly.txt`提供指令对照，`ghidra_project/RemoteRecovery.gpr`可用Ghidra打开继续分析。

本机已通过ARM GCC构建，编译选项包含`-Wall -Wextra -Werror`：

```sh
cd firmware_recovered
make
```

输出位于唯一的`build/`目录：`reconstructed.elf`、`reconstructed.bin`、`reconstructed.hex`和链接映射。它们是**重建版本**，不是原固件备份。本次没有向板子写入这些产物。

重新运行反编译用`bash run_ghidra.sh`。Ghidra安装缓存在`/home/zhangnuo/.cache/codex-tools/ghidra/ghidra_11.0.3_PUBLIC`，也可通过`GHIDRA_INSTALL_DIR`指定其他路径；脚本自动处理中文路径的Jython限制并清理临时文件。

## 已完成验证及恢复范围

`verify_logic.py`使用Unicorn 2.1.4直接执行**原BIN中的Thumb机器码**，与恢复后的C逻辑比较；硬件通信函数被替代为记录调用的桩，不向实际板子发指令。`validation_report.json`记录结果：

| 对照项 | 通过案例 |
| --- | ---: |
| ADC缩放、浮点滤波、16位回绕、限幅和历史值 | 600 |
| 数据包、相邻RAM读取和累加校验 | 200 |
| 按键状态、优先级、微调边界、EEPROM写入请求 | 800 |
| SysTick计数与后置自增的11拍调度 | 256 |
| 合计 | **1856** |

复跑需Python、GCC和Unicorn：在自己的Python环境中安装`unicorn==2.1.4`后，运行`make verify`；也可用`make verify PYTHON=/你的虚拟环境/bin/python`。

仍需区分以下范围：

- 核心业务逻辑通过对照；完整硬件启动、软件总线时序、无线收发和EEPROM电气访问尚未上板验证。
- 用GCC启动代码和软件浮点库替代了Keil运行库，并整理了通用外设函数。GPIO写入的分组、编译后的指令数和延时循环时长会有差别。C结构体布局也不同；数据包依赖的原RAM布局已单独模拟。
- 原EEPROM读取失败时会返回栈残值，重建函数在失败时返回0，这是明确的差异。按键输入在重建中一次读取三个GPIO快照，原程序逐次读取寄存器；信号在一次扫描期间跳变时可能不同。
- 原程序在开启SysTick后才完成外设初始化，且在SysTick中执行EEPROM延时、软件总线和无限等待无线IRQ。这里保留其阻塞结构；中断内的`delay_ms`依赖同一个SysTick计数，不能当作准确的10ms等待。完整时序等价尚未验证。
- 微调检查的是“调整前是否小于/大于±250”，因此异常保存值如249再加5会得到254。按原行为保留，而不是改成新的限幅算法。

这些C文件可作为丢失代码后的继续开发基础。要确认与现有接收端完全兼容，仍需用原备份做恢复保障，并在板上核对摇杆方向、按键和实际无线帧。
